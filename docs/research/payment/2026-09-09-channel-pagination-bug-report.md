# bug: Ant主体流出渠道部分分页查询业务失败，页面切换页码后仍显示旧数据

Observed: 2026-09-09
Scope: payment
Status: snapshot

## 问题摘要

生产环境“流出渠道基础数据管理 → Ant主体流出渠道”在 `EXTERNAL` 场景下，使用页面支持的每页 50 条查询，部分页返回 HTTP 200，但业务失败且无结果数据。该现象已通过页面原生搜索、分页控件和 Python/CDP 查询分别观察到，并非仅发生在脚本重放中。

另有两个关联现象：失败后页码已切换，表格仍显示前一页内容；成功页之间存在内容完全相同的重复行。疑似服务端查询或其依赖处理异常，但具体根因尚未确认，重复行与查询失败是否同源也未确认。

## 环境与范围

- 观察时间：2026-09-09；全页遍历于北京时间 21:34:19 完成。
- 页面：<https://ifundcontrol.alipay.com/productOperation/paymentProductManagement/networkConstruction/channelsManagement>
- 页签：**Ant主体流出渠道**。
- 条件：`payoutType=EXTERNAL`，无其他有效业务筛选，每页 50 条。
- 浏览器：WSL Chrome，通过 CDP 9222 连接用户实际使用的已登录浏览器。
- 数据规模：成功响应一致报告 `totalCount=4914,totalPages=99`。
- 全程仅查询，无生产业务修改。结果限于本次账号视角和观察时段。

## 最小复现步骤

1. 登录生产运营平台，进入上述页面和页签。
2. 选择每页 50 条，保持 EXTERNAL 场景，无额外筛选。
3. 点击第 2 页，确认实际查询成功并显示 50 条数据。
4. 点击第 1 页，同时观察 Network 中查询响应及表格行内容。

本轮第 2 页成功；第 1 页业务失败。回到第 1 页后，页码显示 1，但表格的 50 行单元格内容及顺序与第 2 页完全相同。每次点击后持续观察 12 秒，观察窗口内没有捕获后续成功查询。

通过“搜索”触发第 1 页也复现同一业务错误。此前原生每页 10 条时，第 2、3 页成功，第 4 页失败；不能仅从失败现象推断页大小上限。

## 接口与响应证据

```http

```

```json

```

实际 URL 带 `ctoken`，复现时使用正常登录会话；报告省略凭证值。以下为失败响应的关键字段摘录，并非完整响应：

```json
{
  "success": false,
  "status": false,
  "resultObj": null,
  "msgCode": "IPAY_RS_510090020"
}
```

HTTP 状态为 200。原生 UI 失败响应的错误栈还观察到 `errorName=SERVICE_RESULT_NOT_TRUE`、`errorSpecific=0020`、`systemName=ifundboss`。

## 一轮全页遍历结果

Python 通过已登录浏览器逐页执行同一只读查询，`pageNum=1…99,pageSize=50`。单线程顺序执行，每页之间间隔约 150 ms，无重试；业务失败记录后继续，以测量整个范围的实际结果。

| 指标 | 结果 |
| --- | --- |
| 尝试页数 | 99 |
| 成功页 / 失败页 | 59 / 40 |
| 实际取得行数，保留重复 | 2914 |
| 按完整原始内容比较的不同记录数 | 2625 |
| 内容完全相同的重复行 | 289 |
| 耗时 | 83.79 秒 |

40 个失败页均为 `IPAY_RS_510090020`，均无结果行：

```text
1, 6, 8, 9, 12, 14, 16, 24, 28, 29, 31, 38, 39, 40, 41,
50, 52, 54, 55, 56, 61, 62, 66, 67, 70, 71, 72, 75, 77, 78,
81, 82, 85, 86, 89, 90, 91, 94, 95, 96
```

导出新增 `seqid=1…2914` 仅用于本次文件内编号，未删除重复行。内容比较排除 seqid，不依赖将任何业务字段假定为源系统主键。尚未确认服务端记录身份和排序契约，不将 2625 直接解释为完整业务实体数量。

## 预期行为与影响

- 有效分页应返回该页数据；无法查询时，页面应明确表明当前页未加载成功，避免把旧表格表现为新页结果。
- 在范围与数据稳定、排序确定的条件下，遍历应能够覆盖完整查询结果；需要明确记录身份、排序和总数口径，解释跨页相同内容重复的原因。
- 当前无法依靠该分页查询获得经过完整性校验的全量配置，阻塞 Channel 完整快照的生产验收。
- 人工查看时可能把前一页数据误认为当前页数据。本次未评估实际支付处理是否受影响。

## 建议排查与验收

服务端先对照同一会话下第 1 页失败、第 2 页成功的请求，检查对应日志、下游调用及逐条数据处理异常；核实分页排序是否确定、关联查询是否重复行，以及 totalCount 与结果列表是否使用相同查询口径。这些是排查方向，不是已证实根因。报告未保存请求追踪 ID，需要在复现时从 Network 获取并关联日志。

前端检查失败分支是否保留旧列表、页码与实际数据所属页是否分离，以及错误状态是否清晰可见。

修复后在相同筛选下验证此前失败页，并重新执行全页遍历；依据确认后的记录身份、排序和总数口径检查完整性。另验证失败时页面不会将旧数据表现为新页查询成功。当前证据不能说明所有账号或所有时间都必然失败。
