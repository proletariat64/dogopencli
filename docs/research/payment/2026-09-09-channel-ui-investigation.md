# Channel 页面真实交互与重放差异探查

Observed: 2026-09-09
Scope: payment
Status: snapshot

## 诊断方向

用户反馈正常浏览器前端能够查看全部 Channel，要求优先观察页面真实发出的请求与响应处理。这是明确的诊断线索；[此前的直接重放](2026-09-08-channel-query-contract.md)失败不能证明页面同样失败，更不能先归为后端页大小上限。

规格已发布为 [v0.1.0 Issue #1](https://github.com/proletariat64/dogopencli/issues/1)。公开 CLI＋假 CDP 的 SIT 与生产只读 UAT 是正常验收流程，接入探查可以与规格和实现工作并行。

## 本轮观察

- 首次通过既有 CDP 9222 新建独立标签页进入 Channel 根后，稳定重定向到 `https://ipaybuservice.alipay.com/login.htm`，未进入渠道 iframe，尚未取得 Search 或翻页请求。
- 原成本标签页未被代理操作；页面仍显示不能证明新请求的认证有效。探查标签页已关闭，没有用这次登录状态解释前一天的业务失败。
- 用户随后表示看不到 Chrome 窗口。主线程复查时 CDP 已不可达，专用 profile 未被进程锁定；使用同一 profile、9222 和 WSLg Wayland 重新启动 headed Chrome。
- 一次短暂启动后进程退出，原因未确认；保持启动进程后，CDP 稳定可达，窗口恢复为 normal 并激活登录页。用户随后完成登录，没有切换或关闭其他项目的浏览器。
- 用户要求先检查健康状态。9222 的版本查询和 Runtime 调用成功，既有 Channel 标签页中的业务 iframe 已加载。仅此不能证明新查询成功，因此继续验证页面原生查询。

## 已捕获的原生 UI 请求

在既有登录标签页中仅操作“搜索”和分页控件，通过 CDP Network 捕获页面自身发出的请求：

| 操作 | 请求 JSON |
| --- | --- |
| 默认搜索 | `{"payoutType":"EXTERNAL","pageNum":1,"pageSize":10}` |
| 翻至第 2 页 | `{"payoutType":"EXTERNAL","pageSize":10,"pageNum":2}` |

两者均为 `POST https://ifundboss-api.alipay.com/payout/api/ability/search.json`；URL 查询参数只有 `ctoken`，请求头包含 `Content-Type: application/json;charset=UTF-8` 与 `Accept: application/json`。未发现默认搜索或翻页额外传入隐藏业务字段；尚不能据此排除认证上下文、请求时序或其他请求差异。

初次两次搜索和一次翻页均以 `net::ERR_CONNECTION_RESET` 终止，没有 HTTP 状态或响应体。页面失败后仍保留旧表格，分页控件也可以变化，因此不能用可见行或页码证明请求成功。这与前一天 HTTP 200 下的业务错误是不同现象。

随后主线程检查 API 与 portal 主机，均可完成 TLS 握手；这仅证明当时的主机连接能力。再次操作原生搜索，取得 `success=true`、`resultObj.success=true`，第 1 页返回 10 条，`totalCount=4914`。此时 CDP 和 Channel 查询会话均可用，无须重新登录；前述连接重置的原因尚未确定。

网络恢复后继续使用原生分页控件：

| 每页条数 | 页码 | 实际响应 |
| --- | --- | --- |
| 10 | 1 | 业务成功，返回 10 条，总数 4914 |
| 10 | 2 | HTTP 200，内外层业务成功，返回 10 条、页内唯一 ID 10 个，总数 4914 |
| 10 | 3 | HTTP 200，内外层业务成功，返回 10 条、页内唯一 ID 10 个，总数 4914 |
| 10 | 4 | HTTP 200，外层 `success=false,status=false`，`msgCode=IPAY_RS_510090020`，无 `resultObj` |
| 50 | 4 | 原生选项由 10 改为 50 后保留第 4 页；HTTP 200，业务成功，返回 50 条、页内唯一 ID 50 个 |
| 50 | 1 | HTTP 200，业务失败，`msgCode=IPAY_RS_510090020`，`resultObj=null` |
| 50 | 2 | HTTP 200，业务成功，返回 50 条、页内唯一 ID 50 个 |

上述失败的错误栈含 `errorName=SERVICE_RESULT_NOT_TRUE`、`errorSpecific=0020`、`systemName=ifundboss`；另观察到错误枚举 `IPAY_RS_510681027`，尚未核实其含义，不据此解释根因。未保留错误消息、第三方错误原文或追踪 ID。

10 条第 4 页及 50 条第 1 页失败均由页面自身请求复现，不能再仅归于手写 `fetch` 重放差异。仍未确定具体服务端原因；页内唯一不等于跨页无重复，未将这些局部结果视为完整快照。探查结束时保留用户标签页在每页 50 条、第 2 页，CDP 客户端已断开，Chrome 保持运行。

## 表格实际数据与响应联合复验

用户指出视觉上仍正常刷新，要求不能只判断错误消息。本轮通过 CDP 同时观察查询响应与 DOM 表格数据，每次点击后持续观察 12 秒，记录所有捕获到的 API 请求；记录内容仅在内存中比较，不保存原始行。

开始时控件位于第 99 页，表格实际为 14 条。先回到第 1 页时，接口业务失败；随后以此状态执行完整的“第 2 页 → 第 1 页”对照：

| 操作 | 查询响应 | 最终表格表现 |
| --- | --- | --- |
| 点击第 2 页 | 一次 POST，业务成功，返回 50 条 | 控件为第 2 页；14 条变为 50 条，行内容变化 |
| 点击第 1 页 | 一次 POST，业务失败，`resultObj=null` | 控件为第 1 页；仍有 50 条，所有行的单元格内容和顺序与翻页前完全一致 |

两次均为 `EXTERNAL,pageSize=50`。每次观察窗口内未捕获其他 API 查询或后续成功响应。第二页返回的业务 ID 没有直接显示为 DOM 行键或独立单元格，因此不声称逐 ID 建立了响应与 DOM 的一一映射；保留证据是响应行数、表格行数及翻页前后所有可读单元格和顺序的比较。

这次直接验证了首页失败后表格保留第二页内容，页码变化与视觉上有数据不能证明首页获取成功。该结论限定于本轮操作与观察窗口，不否定其他时间或条件下用户成功查询的可能。此前仅根据错误码推测旧数据不足，本轮补上了 DOM 数据证据。

## 前端静态代码对照

当前页面加载的 `180020010001284233/umi.df3bfb1c.js` 定义了上述 POST 查询服务。`9e65757e-async.16f6b9d1.js` 的 `onTableChange` 读取表单字段，再增加 `pageSize` 和 `pageNum`；`handleSearch` 将 `pageNum` 置为 1。这与实际捕获的默认请求一致。

`excuteSearch` 补齐分页值后调用该服务；成功分支把响应中的 `payoutAbilityVOList` 交给 `getAllResultGrayStatus`，再替换当前表格数据。后者对 `GRAY` 记录额外查询灰度信息，补充 `grayStatus` 和 `ruleDetailObj`；所读代码没有合并其他分页、补回缺失记录或本地去重的逻辑。此处是静态实现观察，不证明本次请求已触发灰度查询，也不将这些附加能力自动纳入 CLI。

请求拦截器向 URL 追加编码后的 `ctoken`，实现包含字符串操作。此前把 URL 对象直接传给页面 `fetch` 的异常可能与此有关，但未经隔离实验确认，不能作为已证实根因。接入应使用字符串 URL；不复制 Cookie/token 值到配置或日志。

## 后续只读验证

1. 继续使用已具备有效会话的标签页，重新获取当前 iframe 执行上下文；不假定旧的 context ID 始终有效。
2. 已确认原生请求同样失败；下一步核实错误枚举含义和失败条件，不继续重复相同失败请求，也不假定更换页大小即可修复。
3. 如得到新的失败条件线索，再以已捕获的请求模板做最小对照，保留网络错误、认证失败和业务失败的区别。
4. 前端灰度补充与原始查询字段分别处理，不将表格可见或翻页控件变化当作查询成功。
5. 仅在请求行为清楚后验证完整遍历、唯一 ID 和版本保留，不跳过失败页或用旧缓存补数量。

上述 UI 对照未执行生产写操作，也未保存原始业务行或凭证。随后按用户要求进行的 Python 全页诊断及私有导出见下节；历史业务失败的具体根因仍待验证。

## Python 每页 50 条完整遍历与 seqid 导出

使用[手工运行的只读诊断脚本](../../../tests/integration/channel_pages_probe.py)，连接既有 CDP 9222 和已登录 Channel iframe，按实际查询契约执行 `EXTERNAL,pageSize=50,pageNum=1…99`。这是显式运行的生产诊断工具，不是正式 CLI 或默认执行的自动测试。依赖当前环境已有的 `websocket-client`。

```bash
rtk proxy python3 tests/integration/channel_pages_probe.py --port 9222
```

本轮仅做一遍顺序遍历，不重试；业务失败页被记录后继续下一页，以观察整个范围，不把失败页视为空页或成功页。认证、解析、上下文等异常中止；默认最多 200 页、600 秒。请求只指向已验证的查询端点，不操作界面或修改业务数据。

| 指标 | 实测结果 |

| 后端报告总量 | 4914 |
| 尝试页数 | 99 |
| 成功 / 业务失败页数 | 59 / 40 |

用户要求为导出增加编号主键。`seqid` 从 1 开始，仅在本次导出内唯一；每个取得的原始行均保留，重复行分别编号。不将 `abilityId` 宣称为已验证的源系统主键，不用新编号证明源数据完整，也不将 seqid 用于跨次导出关联。JSON 数值保持数值类型及 Decimal 精度；源数据若已有 seqid 字段则中止，避免覆盖。

原始导出按本次请求保存在仓库外的私有目录 `/tmp/dogopencli-channel-export-bob78hme/`：`records.jsonl` 为带 seqid 的逐行数据，`manifest.json` 为逐页结果及完整性汇总。目录权限 0700、文件 0600，不进入 Git 或终端日志；临时目录不保证长期保留。成功页在 manifest 中记录对应 seqid 区间，可追溯导出记录来自哪一页。

已独立读取导出文件核对 2914 行及全部 seqid 连续唯一；比较时排除新加 seqid，确认 289 行内容重复。合成验证覆盖重复行分别编号、原字段不变、Decimal 精度和 seqid 冲突拒绝；脚本 Ruff 检查通过。本次遍历覆盖了所有报告页码，但未取得完整数据集。
